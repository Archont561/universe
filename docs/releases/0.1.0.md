Universe 0.1.0 is a linux-64-only pre-release packaging checkpoint, not the integrated v1 release.

`decision-132` defines this tag: four real `linux-64` Conda packages, a rendered publish workflow
with three declared destinations and one hosted index, and a rendered restore entrypoint that
drift-checks against the same manifest. The main-CLI amendment brings `universe-kit` and the
umbrella `universe` facade into the checkpoint, and `UNI-55` adds the separately installable
bootstrapper. `decision-119` still defines the stable v1 release; this tag does not supersede it.

## What this tag contains

- Four `linux-64` Conda packages: `universe-airlock`, `universe-kit`, the umbrella `universe`
  facade, and `universe-airlock-bootstrap`. The workflow that builds and publishes them is
  rendered from `universe.toml` and drift-checked in CI, so the pipeline is a product of the
  manifest rather than a hand-maintained file that happens to work.
- Three destinations, one command each. Every package lands on prefix.dev, on the
  `universe/conda-channel` branch as one snapshot tree, and as a GitHub Release asset of the
  release tagged `packages-linux-64`, whose title is `universe (linux-64) 0.1.0`.
  A release is not done until all three hold the same bytes. The two refs a
  consumer meets are namespaced and declared in `universe.toml` rather than left to the tool's
  defaults: `universe/conda-channel` for the channel and `universe/bootstrap` for the entrypoint.
  A bare `channel` and a bare `bootstrap` claimed the top level of one repository's namespace,
  which reads as if the first project to push owned the name.
- A release is tagged by its address and named by its contents. The tag
  `packages-linux-64` stays put so a link to it keeps working when the next build replaces the
  assets; the title carries the version, because a release that calls itself after its subdir
  makes a reader open it to learn which build they are looking at. Its body is not composed by
  the publisher: `releases.notes` names this file, and the publish job passes `--notes-file`, so
  the text a reviewer read in the pull request is the text the release shows.
- The `universe/bootstrap` ref explains itself. Beside the executable and its descriptor it
  carries a generated `README.md` stating what the ref is, what the binary beside it hashes to,
  and — because the first wrong assumption a reader makes is that a ref in this repository is a
  channel — that it is not one. The page is generated from the bytes in the same commit, so a
  republished binary rewrites the digest rather than leaving a stale one on a page a reader
  would take at its word.
- A fourth destination that holds no bytes: the channel index is served from GitHub Pages at
  <https://archont561.github.io/universe>. The release workflow downloads its own build
  fragments, runs `universe index` over them, uploads the tree as a Pages artifact, and deploys
  it in a separate job that holds `pages: write` and `id-token: write` and nothing else. No
  generated file is committed, so the site cannot describe a channel the release did not
  publish, and a consumer can point a solver at one address without a client or a credential.
- A rendered restore entrypoint **is** committed at this tag. `universe.toml` declares an
  `[airlock.developer.restore]` scope pinned at the published `universe/bootstrap` ref, and
  `.universe-airlock/restore.sh` with its PowerShell twin are generated from it and compared by
  `pixi run airlock-check`. Run against the real remote, the script cloned the pin, matched its
  commit, found the bootstrapper at mode `100755`, and printed `universe-airlock-bootstrap
  0.1.0`; it then stopped at the absent payload manifest, which is what `universe airlock pack`
  writes. The entrypoint restores a payload, and the payload is the producer's job.
- Five verbs are real. `version` and `verify` belong to the installed `universe-airlock` binary,
  and the latter checks a closed payload without activating anything. `restore` belongs to the
  separately built bootstrapper, which materialises that payload into an immutable environment
  and swaps one `current` link. `sandbox` installs a built set of archives into a prefix and
  runs a command inside it, so a person who has just built a package can try it before
  publishing. `index` renders the channel tree that the hosted address serves.

`universe-airlock-bootstrap` is **separately installable** rather than bundled into the consumer,
and it keeps the same version and train as the other three (`UNI-55`). Its declaration carries
**no runtime dependency** — not on `universe-airlock`, not on the producer, and not on registry
tooling — because it is what runs before an environment exists to restore, and the umbrella
`universe` facade does not depend on it (`decision-115`).

The branch channel solves offline. From a fresh
`git clone --depth 1 --branch universe/conda-channel`, three
Pixi projects asking for one package each ran `pixi install --offline` against that local clone
and each printed `The default environment has been installed.`; every installed `conda-meta`
record declares only `__glibc >=2.17,<3.0.a0`. That evidence belongs to run `43230051708`, the
rebuild that followed the recipe fix suppressing a `libgcc` run export a static channel does not
carry, and its destination read-back is the cache-busted prefix.dev publication `93323`. This tag
is cut later, so its own build supersedes those digests; what carries forward is the property, not
the bytes.

The tag run deployed the index. `release.yml` run `43321675310` is green on every job, including
`publish / pages-deploy`, and <https://archont561.github.io/universe/linux-64/repodata.json>
serves the four packages with the digests the `universe/conda-channel` branch serves. The first
tag run was refused there by GitHub's `github-pages` environment, which allows the default branch
until the release tag pattern is added to it as a deployment rule; that setting now exists.

## What this tag does not contain

- It is not reproducible byte for byte, so each build of the same version replaces the previous
  filenames rather than reproducing them.
- The `sandbox` verb isolates the environment, not the machine: it sets `PATH` and
  `CONDA_PREFIX`, removes the host's Python configuration, and discards the prefix, but it
  creates no namespace and denies no egress, and every run says so on stderr.
- A clean-container restore transcript is not recorded, because no container runtime is
  available here. `UNI-53` and `UNI-59` stay open on it.

## Not a v1 release

`decision-119` requires six surfaces for a stable v1. This tag completes none of them:

| v1 surface | State at 0.1.0 |
| :-- | :-- |
| Conda packages and a standards-compliant static Conda channel | four packages, one platform, one hosted static index |
| Cargo sparse index and crate archives | absent |
| Python wheels and a Python-compatible package index | absent |
| npm packages through an npm-compatible registry surface | absent |
| Airlock consumption across the supported ecosystems | one consumer package and one bootstrapper, one platform |
| A browsable static portal generated from a pinned catalog | absent; the Pages site is a channel index with no UI |

Also out of scope: every platform beyond `linux-64` (`decision-132`); a signed sealed payload
(`UNI-55`), so the bootstrap accepts an unsigned payload in the `developer` lane and refuses the
`sealed` lane until a trusted release key is compiled in; and a Pixi-managed environment
(`UNI-51`).

## How this is checked

`pixi run gates` runs the whole suite. `pixi run repo-check` compares the workspace version, the
component recipes, the first versioned section of `CHANGELOG.md`, the newest `v*` tag, and this
file. When a `v0.1.0` tag exists, the check also compares its annotation subject with the first
line above, so the tag cannot be annotated differently from the notes it belongs to.
