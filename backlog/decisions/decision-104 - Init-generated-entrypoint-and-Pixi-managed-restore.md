## Context

The target workflow was explicitly corrected: the target user should run the generated restore entrypoint, not manually install Universe Airlock or run init on the target.

## Decision

`init` belongs on the project/export side and generates configuration, restore entrypoint(s), and a thin bundle workflow. The target entrypoint selects/clones bootstrap content, verifies/launches a native bootstrap, and uses **bundled Pixi** to establish **Pixi-managed Universe Airlock** from local original packages before restoring the selected payload.

Do not make restoration depend on undeclared Internet fetches or a preinstalled language ecosystem. Keep bootstrap/protocol needs minimal instead of linking all future application/UI code into bootstrap.

## Consequences

Bootstrap and payload references must be pinned/verifiable and compatible with the declared target. Installed prefixes remain target-created state, not exported canonical data. Target-state directory and precise generated script/config names are still to be selected.

## Status boundary

Workflow agreed; no initializer and no bootstrap program exists yet. See [lifecycle](../docs/doc-103%20-%20Init-bootstrap-and-restore-lifecycle.md).

**2026-11-06 update.** The restore entrypoint generator exists: `universe airlock render`
writes `.universe-airlock/restore.sh`, `.universe-airlock/restore.ps1` and the README block
from `[airlock.developer.restore]`, and `--check` fails on drift. It pins by **commit** and
verifies that pin after the checkout, which keeps the generated bytes stable across releases
of this tool — a runtime digest in the script would rewrite every consumer's script on every
release. The bootstrapper it hands over to (`restore --commit <pin>`) is still `UNI-33`, and
the initializer proper is `UNI-13`.

## 27 October 2026 refinement

Bootstrap carries the tool-install closure and catalog pins, not the whole project environment. It can establish PATH availability before a profile is fully prefetched; see decision-115 and doc-109.

## 10 November 2026 correction

The status boundary above says "no initializer and no bootstrap program exists yet", and the
2026-11-06 update says the bootstrapper "is still `UNI-33`". Both describe 2026-10-25, not
today: `UNI-33` landed the real `version`/`verify`/`restore`/`doctor` verbs on 2026-11-08, and
`UNI-53` DoD #3 now proves the rendered entrypoint and that binary restoring a real payload in
one process tree. The generated script `exec`s the binary from the pinned checkout but keeps the
caller's working directory, which is where the closed payload (`.universe-airlock/payload`) and
the state root live; a release manifest inside the ref could not name the commit of its own
tree. The bootstrap's `--help` and the rendered README usage block were corrected to say this.
The initializer proper (`UNI-13`), the Pixi handover (`UNI-51`) and the sealed lane (`UNI-55`)
remain open. This is recorded as a correction rather than a silent rewrite of dated statements.

## 12 November 2026 amendment: the ref the entrypoint hands over to is published

The entrypoint `exec`s `$CHECKOUT/universe-airlock-bootstrap`, and until today nothing published
a ref that held it. The bootstrapper shipped as a Conda package (`UNI-55`), which a solver
installs; the entrypoint does not install anything before it runs. So the loop the earlier
entries describe had a hole exactly where the handover happens.

`universe airlock publish-bootstrap` closes it. It writes one ref — `bootstrap` by default — that
holds an executable `universe-airlock-bootstrap` and a `bootstrap.json` descriptor naming its
digest, size and version, and it writes it with the mode the entrypoint's `[ -x ]` test reads. The
ref is **stable rather than per-build**: republishing identical bytes leaves the commit where it
was, so a consumer's committed pin does not move for nothing. Publication is explicit and
producer-side, which is what `doc-103` means by advancing the bootstrap ref last; the facade
routes it to `universe-kit` for the same reason `airlock render` goes there.

`universe.toml` in this repository now declares `[airlock.developer.restore]`, so
`pixi run airlock-check` compares real files instead of asserting that nothing stale was
committed, and `.universe-airlock/restore.sh` is committed. Run against the real remote, that
script clones the ref, verifies the pin, and hands over to the published binary, which stops at
the payload it does not have yet — `[airlock.delivery]` and `UNI-52` own that half. A
clean-container transcript is still missing (`UNI-59` criterion 5), and this amendment claims no
sealed or Pixi-managed restore: `UNI-55` criterion 5 and `UNI-51` remain open.
