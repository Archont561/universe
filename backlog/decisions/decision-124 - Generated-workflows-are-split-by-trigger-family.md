## Context

`doc-2` specifies three generated files, `{ci,publish,upstream-watch}.yml`, hand-listed.
An earlier request in this project was a single autogenerated `universe.yml` holding every
Universe job.

The job catalog has since grown to roughly thirteen jobs across four trigger families and
three distinct privilege classes (`contents: write`, `packages: write`, `id-token: write`).
At that size the single-file argument inverts:

- **Trigger union.** One `on:` block carrying `push`, `pull_request`, `schedule`, and
  `workflow_dispatch` forces every job to gate on `github.event_name`. A separate publish
  file cannot run on a schedule, because it has no schedule trigger — structural safety
  rather than conditional safety that someone can forget to write.
- **Required checks.** A tag-only workflow never reports on a pull request, so listing its
  jobs as required checks produces a permanent "Expected — waiting". Distinct files make the
  set of PR-appropriate checks obvious.
- **Blast radius.** One malformed YAML file currently breaks validation and publication
  together; split, a broken publish file leaves pull-request CI working.
- **Review.** A change to validation should not produce a diff in the job holding
  `packages: write`.

What is lost is small: several digests instead of one, and more files for the renderer to
emit. Drift checking is per file in either design.

## Decision

**One file per trigger family. The file count follows the role and the declared
capabilities; it is always derived, never a mode switch.**

| Role or manifest | Files |
| --- | --- |
| consumer | `universe.yml` only |
| producer, no stores, no adapters | `universe.yml` only |
| + `[[stores]]` | `universe.yml`, `universe-publish.yml` |
| + lock adapters | + `universe-airlock.yml` |
| + `[upstream]` | + `universe-watch.yml` |

| File | Triggers | Contents | Highest privilege |
| --- | --- | --- | --- |
| `universe.yml` | `pull_request`, `push: main`, `push: tags`, `dispatch` | plan, validate, build, audit, verify-artifact, verdict | `contents: read` |
| `universe-publish.yml` | `push: tags`, `dispatch` | publish-channel, publish-static, publish-releases, publish-registry, bootstrap-airlock, verify-index | `packages: write` / `id-token: write` |
| `universe-airlock.yml` | `push: main` (paths), `dispatch` | mirror (matrix over adapters), render-airlock | `contents: write` |
| `universe-watch.yml` | `schedule`, `dispatch` | watch-upstream | `contents: read`, `pull-requests: write` |

The invariant that keeps the main file safe, and the rule to write down for the next
contributor: **no job in `universe.yml` may need an `if:` on `github.event_name`.** The
moment a job needs one, it belongs in another file.

Additional rules:

- **Verification is artifact-scoped.** `verify-artifact` proves that the thing just built
  installs and works, in a clean environment, per platform. `verify-index` proves that the
  *published* copy matches the built digest. Ranges are narrowed on pull requests
  (changed packages, one platform) and complete on tags.
- **Job names are prefixed by file** (`universe / validate`, `publish / releases`) because
  GitHub permits duplicate job names across workflows and required checks are matched by
  name.
- **One bounded escape hatch.** `[workflow] checks` names a fixed list of commands that run
  inside `validate`. Commands are data; the YAML shape stays closed. Arbitrary steps remain
  refused (`doc-113` §Refusals 5).
- **Repository housekeeping is never generated.** A workflow that commits — relocking, or
  promotion — cannot be digest-verified and stays hand-written.
- **Consumer role is four jobs and nothing else**, all at `contents: read`: plan, validate,
  restore-verify, verdict.
- No `continue-on-error`. Failures must be visible in conclusions.
- `concurrency` is per file and per ref, so a tag publish cannot cancel a pull-request run.

## Supersedes

- The single `universe.yml` requirement for all Universe jobs.
- The hand-listed three-file layout of `doc-2`.

The supersession is a reversal, and is recorded as one: the reason the single file was
rejected is size and privilege spread, both of which grew after the original request.

## Consequences

- `universe init` renders one to four files according to the manifest and prints the
  decision, so the mapping is never implicit.
- `universe ci check` verifies every rendered file against one manifest, and fails when a
  declared capability has no file or an undeclared one has a file.
- `doc-2`'s `init --sync-workflows` and `lint --check-workflows` give way to `ci render` and
  `ci check`, because a discoverable verb beats a flag buried on another command.
- The first `universe-release.yml` is hand-written, because a generator cannot exist before
  its own output does. The renderer's first golden test is that it reproduces the
  hand-written file byte-for-byte.
