## Description
<!-- SECTION:DESCRIPTION.BEGIN -->
GitHub issue #120 reports `universe ci render` deleting a `.github/workflows/release.yml`
that the renderer never wrote. Verified on `40bcf1ff`: `write()` walks
`KNOWN_FILES ∪ STALE_FILES` and removes every entry that exists and is not in the rendered set,
with no stamp check and no diagnostic. `check()` reports the same case as
`ci.file.undeclared`, so a repository that never declared a publish lane is told its own file is
in the way.

The collision is structural rather than accidental. `PUBLISH_FILE` is `release.yml` because
prefix.dev matching a trusted publisher on `workflow_ref` needs that basename (recorded in
`UNI-57`'s notes), and another repository's npm publishing lane owns the same name. Renaming is
not available in either direction, so ownership has to be decided by content: every file this
renderer emits starts with `# @generated by universe … <manifest sha256>`, and a file without
that line is not this tool's to rewrite or remove.

The same rule has a second half the issue does not name. When a manifest *does* render
`release.yml` and a foreign file already occupies the path, `write()` overwrites it — the same
silent data loss from the other side. Both directions are one question: what makes a file this
renderer's.

Severity is high because the loss is silent: no warning, no `--force`, no record, and the
post-render `ci check` does not mention the file it removed.
<!-- SECTION:DESCRIPTION.END -->

## Acceptance Criteria
<!-- AC.BEGIN -->
- [x] #1 A known file that does not carry the `@generated by universe` stamp is never removed, and `ci render` reports it to stderr with its path and what to do about it. — `write` returns `Written { written, untouched }` and the CLI turns `untouched` into a `ci.render.untouched` warning on stderr; `a_workflow_this_renderer_did_not_write_is_never_deleted` and `a_foreign_release_workflow_survives_a_render_and_is_reported` (CLI, through `run`) pin it.
- [x] #2 A stamped file that this manifest no longer renders is still removed, so a rename stays complete rather than leaving a second workflow behind; a fixture asserts the removal. — `writing_the_workflow_set_removes_the_legacy_publish_file` now writes the legacy file *with* the stamp, which is what it looked like when this renderer owned it; `dropping_the_package_lane_removes_the_file_it_rendered` covers the same rule from `UNI-78`'s direction.
- [x] #3 A known file that does not carry the stamp is not overwritten either, even when the manifest renders that name: the run refuses and names the collision rather than replacing a file the renderer did not write. — the check runs before anything is written, so a refused render leaves the tree untouched; `RenderError::Foreign` names the path and `a_foreign_release_workflow_is_not_overwritten_and_the_collision_is_named` asserts both the refusal and the absence of a partial write.
- [x] #4 `ci check` reports the two cases distinctly — a stamped file this manifest no longer calls for (regenerate) and a foreign file occupying a rendered name (move it or reconcile the lane) — instead of one `ci.file.undeclared` for both. — `ci.file.undeclared` is stamped-only, `ci.file.foreign` is the collision, and a foreign file at a name the manifest no longer renders is not reported at all: `check_separates_a_file_we_own_from_a_file_we_do_not` and `check_refuses_a_foreign_file_but_calls_it_foreign`.
- [x] #5 The ownership rule is stated where a reader of the workflows meets it, in `docs/WORKFLOWS.md`, as the reason the first line of every generated file exists. — the bullet "The generated files own themselves, by content" gives the basename collision as the reason and both consequences.
<!-- AC.END -->
